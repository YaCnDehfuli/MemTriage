ML-guided memory analysis, down to the bytes.

A memory image captures the programs and data present on a computer at one moment. MemTriage connects evidence-based triage, a trained model, and address-level inspection in one local workspace. You can move from a process worth investigating to the code behind a prediction, then document what the evidence supports.

MemTriage keeps the mapping from input bytes to image patch to memory address, and gives the analyst tools to examine that address. 01 · End-to-end pipeline

From an image to a question you can investigate.

The workflow first establishes context across the captured system. Detailed model analysis begins when the analyst chooses a process. This keeps expensive inspection focused and preserves the surrounding evidence needed to interpret it.

  1. 01 / INTAKE

    Capture the context.

    Upload Windows memory, identify its hash, and choose the extraction checks.

  2. 02 / TRIAGE

    Find leads.

    Review scored processes, connections, and persistence artifacts, with their supporting rules.

  3. 03 / ANALYSIS

    Follow model attention.

    Classify a chosen process and inspect the memory regions mapped to its grid.

  4. 04 / ASSESSMENT

    Explain the findings.

    Select exhibits, record interpretation and confidence, and preview reports.

What goes in

One Windows memory image, or up to five snapshots of the same host. The API streams uploads in bounded chunks and records their SHA-256 hashes. Configured size and format checks reject unsuitable inputs before a worker starts extraction.

Collection happens outside MemTriage. The tool does not acquire live memory or supply a ground-truth label for an uploaded image.

What comes out

Raw plugin JSON, scored leads, a process grid and verdict, an address-linked region manifest, and bounded static analyses. Investigation and process result files retain the connection between these artifacts.

The reporting stage adds analyst-selected evidence and interpretation. An exported assessment is distinct from the underlying automated observations.

02 · Extraction and prioritisation

Establish context before classifying a process.

Volatility reconstructs Windows structures from the image. VolMemLyzer runs the selected plugins and combines their outputs into interpretable leads. This rule layer and the learned classifier answer different questions.

Choose the coverage.

Light, Deep, and Custom plans control which plugins run. Process lists and scans, parent relationships, network records, suspicious allocations, and registry evidence provide complementary views of the same captured system.

The workbench exposes plugin status and outputs. Table and CSV views come from saved JSON; viewing an artifact does not require another extraction run.

Understand the ranking.

Scored objects retain the rules and evidence contributing to their scores. Conservative, Balanced, and Aggressive profiles adjust prioritisation, while confidence and correlation controls help focus review.

Re-scoring uses retained artifacts. A score is a triage priority, not a model probability. ATT&CK labels describe technique alignment; they do not establish that the corresponding behaviour occurred.

Reuse analysis without confusing its provenance.

Plugin outputs live in the persistent data volume. Reuse checks the image hash, requested plugin plan, schema, extraction health, and artifact validity. Compatible outputs from an earlier investigation can be copied into the current one. Force refresh bypasses reuse. A failed or partial extraction does not qualify as a complete cache hit.

Progress reports plugin states and completed work rather than an invented time estimate. Failures remain visible with diagnostics. The published worker code also preserves usable partial results when a run is stopped or interrupted, so incomplete coverage can be reviewed explicitly.

Implementation: extraction and cache validation · plugin scheduling. Details: scoring rules · local catalog measurement · VolMemLyzer project report.

03 · The learned representation

Turn process memory into a model input.

VADViT is a vision transformer applied to a structured representation of process memory. A virtual address descriptor (VAD) describes a memory region. MemTriage extracts eligible executable regions and renders one region into each image patch.

Preserve the representation the checkpoint was trained on.

The selected PID is extracted from each supplied snapshot with windows.vadinfo --pid … --dump. The backend chooses the snapshot with the most eligible regions; the later snapshot wins a tie. It does not fuse bytes from different moments into one synthetic process.

Eligible executable regions are ordered by category and address: executable allocations first, then DLL-backed regions. In the default configuration, each becomes a 32 × 32 RGB patch. A 7 × 7 arrangement produces a 224 × 224 image. More than 49 eligible regions are truncated to the first 49 in that order; fewer regions leave zero-filled patches.

R / metadata

Region properties

A constant patch value combines the VAD tag with the configured protection mapping. The mapping distinguishes execute/read/write from execute/write-copy protection; other values use the renderer’s default.

G / entropy

Local byte variation

Sliding-window Shannon entropy is reshaped and normalised into a spatial channel, describing how byte variation changes through the region.

B / transitions

Adjacent byte patterns

A 256 × 256 byte-transition table is transformed and pooled to patch size. It describes which byte values follow one another.

region bytes + metadata → 32 × 32 RGB patches
ordered regions          → 7 × 7 grid → 224 × 224 input
trained transformer      → 9 class scores + patch attention
patch index              → original region address + retained bytes

Trained inference is available.

The repository supplies Multi_32_224_6f_3u.pt through Git LFS and a matching label file. The backend reproduces the vit_base_patch32_224 model layout with a nine-class head, then applies RGB conversion, resizing, and ImageNet normalisation before inference in evaluation mode. The default runtime uses the CPU.

The labels are Backdoor, Benign, Exploit, HackTool, Hoax, Rootkit, Trojan, Virus, and Worm. Softmax scores describe this classifier’s output. They are not independently calibrated probabilities of compromise.

Runtime ownership is explicit.

MemTriage owns dump-to-grid preprocessing and model inference. The pinned VADViT submodule supplies the research implementation and reference; the worker image does not copy its training code.

Weights load lazily from local storage, with no pretrained-weight download during inference. The default deployment disables placeholder classification. Missing weights, dependencies, or input produce an unavailable verdict with a reason.

Coverage matters. This is an executable-memory representation of one selected snapshot. The 49-patch limit, region ordering, capture completeness, and training distribution constrain what the prediction can describe. Model attention cannot reveal code excluded from the input.

04 · From attention to inspection

Follow the patch back to its bytes.

The connection is deterministic: the same ordered region list renders the grid and maps patch indices back to addresses. Attention becomes a route into inspection, alongside region size, protection, backing file, and content hash.

The backend reconstructs the final transformer block’s class-token attention to patches and averages across heads. Displayed weights are normalised relative to the grid. A region at 100% is the highest relative attention value in that result; it is not “100% malicious.” Attention is neither a causal explanation nor evidence that those instructions executed.

ViewImplementationWhat it establishes

Bound the cost of inspection.

The worker analyses the top five ranked regions by default. The first receives a 256 KiB decoding budget; four runners-up receive 64 KiB each. Instruction, block, function, string, and hex limits bound additional work.

Partial coverage is carried into the output. A large region is not described as completely decoded because one bounded window was inspected.

Keep useful results when a component fails.

The region report guards each analyser separately. A disassembly failure can leave structure and string results available, with an explicit reason for the missing view.

Manifest records retain patch index, address, protection, backing, size, and hash. Region-analysis JSON separates structural observations, indicators, and summaries.

05 · Software architecture

Separate the interface, jobs, and evidence.

Long extraction and inference jobs run outside the request path. The browser works with structured results and job state; workers parse the memory image; durable storage keeps the artifacts and analyst decisions available across sessions.

06 · Worked investigation

A model lead becomes a testable hypothesis.

The saved controlled experiment shows the complete chain without treating a prediction as a confirmed incident. It uses 2580_5.vmem, a 4,412,228,315-byte image, and examines PID 2580, malware.exe, a WOW64 process.

Coverage of this saved run

118 processes were inventoried and 33 objects surfaced for review. The record lists 22 requested plugins and reuse of local extraction artifacts. Triage used the Aggressive profile, a 20% confidence floor, and no correlation requirement.

Extraction returned 80 VADs; 49 regions entered the grid and five received static analysis. These are coverage counts for one examination, not a throughput or detection benchmark.

Prediction versus evidence

80.47% Exploit class score

The strongest prediction was Exploit, followed by HackTool at 9.33%. The highest-attention region was a DLL, not the private allocation that became the principal forensic lead.

The analyst’s question became: does the private executable allocation contain code consistent with a loader, and what corroborates that interpretation?

Why the 8 KiB allocation deserves review

Region 0x2ea0000–0x2ea1fff is private memory with read/write/execute protection and no backing file. An x86 listing includes fs:[0x30] access at 0x2ea0b79, followed by access through offset 0x0c. Those bytes support a PEB/loader-access interpretation. Suspicious-allocation output agrees that the region warrants review, but it comes from the same capture rather than independent ground truth.

Assessment: investigate this allocation as possible loader or payload code at moderate confidence. The snapshot does not establish execution of the sequence, the allocation mechanism, a particular exploit, or cross-process injection.

Context changes the interpretation.

The experiment creator identified the scheduled task, log_pid.ps1, and export_logs.ps1 as collection infrastructure. They should not be reported as attacker persistence simply because triage surfaced them.

A recorded connection to port 443 lacks reliable PID attribution. It cannot be tied to the selected process or an embedded URL on port number alone.

Inspection also exposes uncertainty.

Several DLLs have i386 metadata while a saved listing used x64 decoding. Three large region analyses were partial. Neither malformed decoding nor absence of a PE signature alone proves malicious modification.

Follow-up should validate architecture, compare file-backed bytes with trusted modules, and correlate execution and network evidence.

Evidence: saved structured analysis · walkthrough and interpretation · technical review notes. No fresh analysis or independent outcome validation was performed for this report.

07 · Reporting as the final pipeline stage

Carry the evidence into the assessment.

The application structures the report; the analyst chooses the evidence and owns its conclusions. Reporting is the final stage of the investigation, after extraction, classification, and inspection.

Pin scored objects or analysed regions, add evidence notes, and distinguish suspected activity from collection artifacts. Analyst confidence and disposition sit alongside the source observations rather than replacing an engine score. Review the findings and narrative, then preview a technical or executive document and print it to PDF. Raw investigation JSON remains separately exportable.

Technical case report ↗

Six pages covering the examination, selected evidence, model output, region inspection, and interpretive limits.

Executive case report ↗

A one-page assessment of the principal lead, confidence, limits, and recommended follow-up.

These supplied PDFs are reviewed case documents, preserved unchanged with their technical and executive notes. Their exhibit selection differs from the selection visible in the recording. This HTML page is the technical report about the whole tool; the PDFs demonstrate its case-reporting output.

08 · Deployment and input boundaries

Keep untrusted parsing behind a controlled boundary.

The local Compose stack separates the worker’s internal network from the services that face the browser. Model inference uses local weights; Windows symbol retrieval uses a dedicated proxy and persistent cache.

Worker isolation

The worker has no direct/general internet egress. It runs on Docker’s internal network with dropped capabilities, no privilege escalation, and an 8 GiB memory limit. The API and UI bind to localhost in the default stack.

Upload limits, validated artifact paths, bounded analysis, and escaped report text address different input surfaces. These controls constrain exposure; they do not make every parser infallible.

Symbols without a general internet route

symbolproxy allows the configured Microsoft and Volatility symbol hosts. It upgrades HTTP requests to HTTPS, restricts destinations to port 443, checks redirects, caps responses, and logs retrievals.

Downloaded symbols persist under /data/symbols. Fully offline operation uses pre-fetched symbols and MEMTRIAGE_VOL_OFFLINE=true; the setup is documented separately.

Implementation: network and container settings · symbol proxy · upload limits · output sanitisation. Guidance: symbols and offline setup · security scanning · disclosure policy.

09 · Verification and limits

Test the connections, then state what remains unknown.

The repository contains tests for the representation, inference contracts, extraction behaviour, region wiring, and report assembly. These check software behaviour. They do not establish a detection rate for real incidents.

None of these alone proves execution, intent, or compromise. This page documents implementation and a saved example, not a new model evaluation.

10 · Run and explore

Start locally, then inspect the source.

Install Git, Git LFS, and Docker with Compose v2. The launcher prepares the pinned components, fetches the model if necessary, and builds the local stack.

git lfs install
git clone --recurse-submodules https://github.com/YaCnDehfuli/MemTriage.git
cd MemTriage
./deploy/up.sh

Open localhost:5173, upload a Windows memory image, and start with Light triage. Follow extraction health, choose a process, and inspect the model-linked regions before selecting report exhibits. In an existing checkout, run git lfs pull before launching.

Docker volumes retain investigation artifacts and database records. Builds require the recursively initialised VolMemLyzer and VADViT submodules. The backend owns preprocessing and runs inference locally with the bundled weights.
